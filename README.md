# Naarad

The production static site for [naarad.io](https://naarad.io), served from the repository root by GitHub Pages. Everything under `app/` is loaded by the browser as written. One build step turns the app into a static HTML page per address, so crawlers and slow phones get the content without running any script; the generated pages are committed, because Pages serves the repository as it is.

**After changing a view, the shell or the content, run `node scripts/build-site.mjs` and commit what it writes. Before committing, run `bash scripts/verify.sh`.**

## How it is put together

```
app/
  shell.html        the page template: head, header, footer, an empty #app-content
  main.js           router and page registry; loads a view module and its
                    stylesheet on demand and keeps the head in step with the page
  urls.js           the address scheme, and the conversion of old addresses
  seo.js            what meta() returns; site, organisation and breadcrumb JSON-LD
  base.css          design tokens, shell, and the primitives every page shares
  data.js           the route model (editorial routes, recorded tracks, catalogue)
  media.js          responsive <picture> markup with the licence attached, and
                    the photograph's own shape reserved so a late image moves nothing
  previews.js       static route maps and elevation profiles drawn from real data
  audio.js          the listening bar, which survives navigation between views
  icons.js          inline line icons
  map.js/map.css    the interactive Leaflet map, imported only by a route page
  journey-store.js  My Journey, kept in this browser
  studio-store.js   Creator Studio drafts, kept in this browser
  views/            home, explore, route, story, studio, journey, info (About, 404)
content/
  routes.source.json  the routes as written, with stop coordinates and text
  routes.json         the runtime file: adds the route line, distances, elevation
  stories.json        short stories, undated until a real date is known
  photo-sources.json  every photograph's author and licence
  practical/          sourced visitor facts for the routes that have stops
  lastmod.json        what each sitemap page said when it was last dated (generated)
Images/photos/      AVIF and WebP at the widths the layouts ask for
Images/og/          1200 x 630 share cards and their photo credits (generated)
scripts/            build-site.mjs, sitemap.mjs and og-card.html (pages, cards,
                    sitemap), verify.sh, and the scripts that produce the content
                    files above
tests/              unit tests that need nothing but node (node --test)
e2e/                Playwright checks (cd e2e && npm install && npm test)

Generated by scripts/build-site.mjs, never edited by hand:
index.html, 404.html, routes/index.html, routes/<slug>/index.html,
explore/, stories/, creators/, journey/, about/, Images/og/, sitemap.xml,
content/lastmod.json
```

Desktop and phone share one route model and one map. Where only width changes, a
component reflows; where the interaction model differs, the composition does. On a
phone the route page leads with the map and raises the story in a sheet, with the
walk actions fixed in reach — it is not the desktop spread made narrow.

Breakpoints: 1240px (tablet/compact desktop), 1023px (tablet), 639px (phone).

## Addresses

Every page has its own address. `app/urls.js` builds them and `app/main.js`
resolves them; later sections depend on this scheme, so keep it:

```
/                        home
/routes/                 route catalogue; ?q= fills its search (the header search sends it here)
/explore/                the same catalogue; its canonical is /routes/
/routes/<slug>/          a route; the open stop is a query, /routes/<slug>/?stop=3,
                         and the canonical never carries it. A route with no published
                         stops is noindex,follow and not in the sitemap (below)
/stories/                story index
/stories/<slug>/         a story
/creators/  /about/      the studio and About
/journey/                My Journey, kept on the visitor's device: noindex, not in the sitemap
/blog/  /blog/<slug>/    reserved for the blog
```

Route pages sit beside the recorded-track data in `routes/` (`routes/*.geojson`,
`routes/*.gpx`, `routes/geo-tracks.json`), which `app/data.js` still reads from
there. Slugs come from `data.js` and are always `[a-z0-9-]`.

Old addresses keep working. On the homepage, `/?route=x[&stop=n]`, `/?story=x`
and `/?view=v` are rewritten in place (`history.replaceState`) to the clean
address and that page is drawn. The old path forms `/route/x` and `/story/x`
have no file, so GitHub Pages answers with `404.html`, whose first script sends
the reader on before anything paints. `legacyTarget()` in `app/urls.js` does the
conversion and `tests/urls.test.mjs` pins every form of it.

Navigation never leaves a link dead: a click draws the page in place, and when
its view or data cannot be fetched the browser loads the address itself. A link
to the page you are on adds no history entry, and an in-page `#anchor` only
scrolls (it fires `popstate`, which `main.js` ignores when just the hash changed).

## Pre-rendered pages, structured data and share cards

`node scripts/build-site.mjs` starts a small static server that answers every
page address with `app/shell.html`, opens each one in the Playwright Chromium
from `e2e/node_modules` with `window.__NAARAD_PRERENDER__` set, and saves the
document `app/main.js` draws. In that mode the app mounts no map (the route page
keeps its static SVG preview), starts no motion, registers no service worker,
and reads nothing from the visitor's device. It writes:

- one `index.html` per address above (from `publicPages()` in `app/main.js`),
  and `404.html`: a noindex not-found page that links to `/routes/` and `/stories/`;
- `Images/og/<card>.jpg`: a share card per route and story, and for home, the
  catalogue and the story index, drawn from `scripts/og-card.html` in the site's
  fonts. A card uses the page's own photograph only when its licence in
  `content/photo-sources.json` allows adaptation (CC0, Public Domain Mark, CC BY,
  CC BY-SA); the credit is printed on the card and recorded in
  `Images/og/manifest.json`. A route with no photograph shows its recorded line,
  or the wordmark;
- `sitemap.xml` and `content/lastmod.json`: see below.

The build is deterministic: the same repository gives byte-identical files, and
a file is only rewritten when it changed. It is also all or nothing. A page that
fails to load, a request that fails, a console or script error, or a content
file that is not valid JSON stops it with a non-zero exit before a single file
is written or deleted. It will not delete the pages and cards it wrote earlier
(it finds its pages by the marker comment on their second line) unless you pass
`--allow-removal`, so a typo in the content cannot quietly take pages off the
site; removing a page on purpose is `node scripts/build-site.mjs --allow-removal`.

### The sitemap and its dates

The sitemap lists every page whose canonical is its own address and which is
not noindex. Its `<lastmod>` is the day the page's content last changed, and
that day is remembered in `content/lastmod.json`, committed beside it: for each
page, a hash of what the page says (its main content and the head tags it owns:
title, description, canonical, share tags, JSON-LD) and the date that hash was
first built. A build keeps a page's date while its hash is the same, and gives
a new or changed page the build date, which is today's date or
`NAARAD_BUILD_DATE=YYYY-MM-DD` when that is set. The clock is read for nothing
else. The header, footer and scripts every page shares are not part of the
hash, so changing them dates no page.

This is why the dates do not depend on git: a shallow clone, a rebase, a
cherry-pick or a copy of the tree with no `.git` directory all build the same
file, and rebuilding never moves a date. Do not edit `content/lastmod.json` by
hand; commit it with the change that moved it. (`scripts/sitemap.mjs` holds the
logic; `tests/sitemap.test.mjs` and `tests/build-lastmod.test.mjs` pin it.)

### Routes with no stops

Only a route with published stops (today Hampi, Thanjavur and Auroville) has
content of its own. The other routes are catalogue rows and recorded GPS tracks
with a headline fact or two. Their pages stay reachable and linked, but they are
`noindex,follow`, are left out of the sitemap, and carry no `TouristTrip` data:
a stand-in distance in `discover/seed-tours.json` is not a trip to describe, and
a snippet or share card never states it. A route leaves this state on its own
the day it gets stops (`isStub` in `app/views/route.js`).

When a visitor opens a pre-rendered page, `#app-content` carries
`data-prerendered="<address>"`. `main.js` renders the view again, and when the
markup is the same it keeps the DOM untouched and only adds what markup cannot
carry: the Leaflet map, the story scroll watcher, motion for what is still below
the fold. Device-local pages (My Journey, the studio drafts) are replaced when
the visitor has data of their own.

Each view's `meta()` describes its page (the shape is documented in
`app/seo.js`): title, description, canonical `path`, `robots`, the share `card`,
the hero `preload`, and `schema`, the JSON-LD nodes. `setMeta` in `main.js`
writes all of it as one block of `data-page` tags after `<title>`, both when
pre-rendering and on every client-side navigation. Home carries WebSite (with a
SearchAction on the catalogue search) and Organization; every other page a
BreadcrumbList; routes a TouristTrip whose itinerary lists the stops as
TouristAttractions with coordinates; stories an Article by Naarad editorial,
about the route and mentioning its stop, dated only when the content records a
date. schema.org gives a Trip no distance or duration property, so a route's
distance sits on a TravelAction and its walking time stays on the page.

### Adding a page or a section

1. Write `app/views/<name>.js` exporting `render(context)`, `meta(context)` and
   `stylesheet` (see `app/visual-contract.md`), and add it to `moduleFor` in
   `app/main.js`.
2. Add an entry to `PAGES` in `app/main.js`: a fixed `path`, or a `prefix` with
   `load(slug)` and `list()` for one page per item. The blog is two entries,
   `/blog/` and the `/blog/` prefix.
3. Build links with `app/urls.js` (add a path helper there), and return
   breadcrumbs and any JSON-LD from `meta()`.
4. Run `node scripts/build-site.mjs`. The page, its card and its sitemap entry
   follow from the registry; nothing else has to change.

## The data, and what is not there

Nothing on the site fills a gap with a plausible-looking number, date or claim.

- **Route lines.** An editorial route's line is interpolated between the real
  coordinates of its stops; the data records it as a connecting line and the page
  says so. The Chennai routes in `routes/geo-tracks.json` are real recorded tracks
  and are marked as such.
- **Elevation.** Sampled from NASA SRTM 30 m through OpenTopoData along the route
  line, at about 90 m spacing. Ascent and descent are computed from those samples
  with a 3 m threshold. A route without samples shows an empty state, not a curve.
- **Photographs.** Found through the Openverse API under CC0, Public Domain Mark,
  CC BY or CC BY-SA only. Author and licence are recorded per file in
  `content/photo-sources.json` and shown on the page.
- **Narration.** No creator has recorded any yet. The listening bar reads the
  published text aloud with the device's own speech synthesis and labels it as
  such; it switches to a recording as soon as a stop carries one. No page,
  description or share card promises recorded audio.
- **Creator publishing, transcription, translation, offline bundles and accounts**
  need the Naarad backend. The interface says so where you meet them. There are
  no accounts, no downloads, no app and no paid plans, and nothing public says
  otherwise.
- **Dates.** A story has no publication date until a real, checkable one is
  known; then `published` in `content/stories.json` fills the page, the Article
  data and the share tags together. Nothing is back-dated to look established.
  The sitemap's `lastmod` is the day the page's content changed (above).
- **Catalogue rows.** `discover/seed-tours.json` is a stand-in for a tours table
  that does not exist yet. Its distances, durations and ascents are not
  measurements, it carries no ratings (the old demo ratings are gone), and the
  search snippets, share cards and structured data never state them. Recorded
  tracks have their real GPS length.
- **Descriptions** say what the page has: the studio keeps drafts in the
  browser and publishes nothing; the catalogue says how many routes have stops;
  the stories are short.

## Rebuilding the generated files

```bash
python3 scripts/build-photos.py     # fetch and encode the photography
python3 scripts/build-routes.py     # route lines, distances, elevation profiles
python3 scripts/build-fonts.py      # subset the fonts to woff2
node scripts/build-site.mjs         # pages, share cards and sitemap: run last, after any of these
```

`build-photos.py` crops the black bars off the uploads listed in `LETTERBOXED`
before it encodes them.

`scripts/build-photos.py` takes ids as arguments to refresh a single photograph.
Originals are cached in `.cache/photos` and are not committed.

## Development

Serve the repository root with a static server that behaves like GitHub Pages
(a folder serves its `index.html`, an unknown path gets `404.html`):

```bash
node e2e/serve.js                   # http://127.0.0.1:4173
```

An address with no generated page yet (a route added since the last build)
still works there and on Pages: `404.html` loads the app, which draws the page
if it exists. Its status stays 404 until you rebuild.

### Checks

```bash
bash scripts/verify.sh
```

runs all of it, prints a PASS or FAIL line per step and exits non-zero if any
failed:

1. the build is deterministic: `node scripts/build-site.mjs` twice gives the same
   pages, cards, sitemap and `content/lastmod.json`, and what it gives is what is
   committed (commit the generated files with the change that caused them; while
   that is still uncommitted, `VERIFY_ALLOW_UNCOMMITTED=1 bash scripts/verify.sh`
   skips the comparison with the commit);
2. `node --test tests/*.test.mjs`: unit tests with no dependencies (Node 22 or
   later): the address scheme, the sitemap dates, the service worker run in a
   sandbox, the loaders, what each page claims about itself, and the build
   failing safely (those run the real build in a copy of the site, so they need
   Chromium like the build does);
3. `node scripts/check-practical.mjs` once that script is in the tree;
4. the Playwright checks in `e2e`, which cover both compositions, the clean
   addresses, canonicals, the pre-rendered HTML and its structured data, the
   sitemap, what happens when a fetch fails, history and anchors, layout shift
   at tablet widths, and the service worker. They need `cd e2e && npm install`
   once, and the generated pages to be current (`verify.sh` builds first).

### The service worker

`sw.js` serves app code cache-first, pages network-first (offline, the copy
from the last visit or else the shell, which draws the page from cached
content), content network-first, and photographs and map tiles as they are
used. "Network" means the server: GitHub Pages lets a browser keep a file for ten
minutes, so pages and content are revalidated (`cache: 'no-cache'`) and what is
stored under a version is fetched past the HTTP cache (`cache: 'reload'`); the
app's own `fetch` calls revalidate for the same reason. **Bump `VERSION` in
`sw.js` whenever the shell, a view module or a stylesheet changes**, or visitors
keep the old one.

A new worker takes over at once, and a page that was already controlled reloads
once when that happens (`app/shell.html`), so old and new modules never run
together. Visitors who still have the worker from before pages had addresses
(v10, or v11 of a test build) have it clear itself once: a script in the shell
removes it and its caches and loads the page again. That script can go once
enough time has passed that those visitors have all been back.

## Files that must stay

- `googlecc72b0f2c9685bc7.html` proves to Google Search Console that naarad.io
  belongs to us. Google re-checks it periodically, so deleting it un-verifies
  the site and stops Search Console data. Keep it at the root, unchanged.
- `CNAME` points GitHub Pages at the naarad.io domain.
